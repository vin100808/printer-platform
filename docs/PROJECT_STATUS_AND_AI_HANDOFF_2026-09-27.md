评估日期：2026-09-27  
项目：printer-rental-platform（package 版本 0.1.0）  
代码基线：`7c15a00`；评估时另有三份未跟踪的 `_CODEX.md` 业务文档。  
用途：让业务负责人了解系统现状，并把本报告直接交给新的 Chat 讨论 AI 方案，无须先读取整个仓库。

## 1. 结论：能用，但目前适合有人复核的内部运营试用

系统已经具备客户、订单、设备、抄表和运营金额测算的主干，并非只有界面原型。日常建档、登记设备、录入抄表有实际实现，核心计算也有测试。

但不建议将当前结果直接作为无人复核的正式账单，更不建议让 AI 直接批量修改数据库。优先问题是历史数据一致性与保护，而不只是缺少 AI：补录历史抄表会留下后一期的旧用量；删除运行中设备可能连带删除抄表；缺抄表的期间不会自动变成完整待结账单。

对“使用起来有问题吗”的回答是：**有，少量数据、熟悉业务的人手工操作可以试用；手机后台使用、历史修正、完整对账和多人并发操作仍有明显缺口。** 本次没有完成登录后的逐页视觉验收，因此这里是代码与运行检查支持的判断，不是完整用户体验验收结论。

## 4. 最优先处理的问题

### P1：历史抄表补录或修改后，后一期用量不联动

**代码确认。** `src/lib/meter-admin.ts` 新增只创建目标记录，编辑只更新目标记录。编辑时下界使用原保存的 `previousBwReading/previousColorReading`，没有重新取实际上一期；也没有更新下一期基数和用量。

例：6 月累计 5,000；先录 8 月累计 9,000，8 月用量保存为 4,000。随后补录 7 月累计 7,000，7 月用量是 2,000，但 8 月仍为 4,000，而正确的相邻月份差额应为 2,000。于是 7–8 月合计由应有的 4,000 变成 6,000，并可能影响超印费。现有集成测试覆盖了插入成功，却没有断言下一期随之更新。

处理目标：明确历史变更、后一期重算及已报账金额修订规则；变更应原子执行并保留前后值。确认前不要让 AI 自动补录跨期记录。

### P1：可删除已有抄表的运行中设备

**代码确认。** `src/actions/printers.ts` 的 `deletePrinter` 仅阻止 replaced/removed 状态；`prisma/schema.prisma` 的 MeterReading → Printer 关系为 `onDelete: Cascade`。因此 active 设备删除时可以带走抄表历史。

处理目标：有业务历史的设备改为作废或归档；删除前检查关联数据；保留操作记录。现阶段避免把“删除设备”当作普通纠错方式。

### P1：结算摘要不是完整账单

**实现边界确认。** 订单详情只取每台设备最近三条抄表；按已有抄表计算，再汇总最近月份/季度。缺抄表设备/月份没有进入金额结果。虽然界面有参与台数等信息，但没有完整的应结设备、应结期间覆盖检查和锁账机制。

例如一张订单有两台在场设备，当月只有一台抄表，汇总仍可以出现一个金额，它不能被理解为整单最终应收。即便设备当月没有超印，缺少抄表也不代表月租自然免收。

处理目标：按指定期间建立应结清单，明确缺失、暂估、已复核和最终确认状态；不要把空值当 0。AI 回答金额时必须同时说明期间、覆盖台数、缺失项及是否最终确认。

### P1：新流程的供应商成本链条尚不完整

订单可以有供应商，但金额计算仍从设备关联的旧 `SupplierOrderItem → SupplierPackage` 取得供应商价格。新流程允许该关联为空，结果会显示应付/毛利不可计算。这种降级本身合理，但“已选供应商”不等于“可算成本”。

处理目标：先确定运营方如何在新流程维护供应商价格及版本，再谈 AI 自动利润分析。缺供应商价格不能估成零成本。

| 抄表日期依赖服务器时区 | `meterWindow` 使用本地日历方法，Dockerfile 未明确业务时区 | 固定并测试上海时区月末/1 日/3 日边界 |

## 7. 给下一段 Chat 的技术与业务背景

### 技术结构

Next.js 16 / React 19 / TypeScript 单体应用；Node 要求 >=22；Prisma 6 + PostgreSQL；MinIO/S3 存文件；Tailwind；Zod 校验；Decimal.js 计算金额；Vitest 测试。

界面使用 App Router。写操作主要是 Next.js Server Actions，分布在 `src/actions/`；业务计算与校验在 `src/lib/`；并非已有可供外部 AI 直接调用的标准业务 REST API。当前 API 路由主要为健康检查与附件读取。

关键代码索引：

- 数据模型：`prisma/schema.prisma`
- 登录与授权：`src/lib/auth.ts`、`src/actions/auth.ts`
- 订单写入：`src/actions/orders.ts`
- 设备生命周期：`src/actions/printers.ts`
- 客户及后台抄表入口：`src/actions/meter.ts`
- 历史补录、更正：`src/lib/meter-admin.ts`
- 用量、期间与输入校验：`src/lib/meter.ts`
- 金额算法：`src/lib/settlement.ts`
- 订单结算展示取数：`src/app/(admin)/orders/[id]/page.tsx`
- 附件存储：`src/lib/object-storage.ts`

### 核心关系

Customer → CustomerOrder → CustomerOrderItem → Printer → MeterReading。

CustomerOrderItem 绑定具体 CustomerPackage 版本；Printer 绑定 MachineModel。订单可绑定 Supplier；供应商计费仍依赖可空的历史 SupplierOrderItem/SupplierPackage 关系。不要因业务名叫 Order 就假设数据库模型也叫 Order：实际是 CustomerOrder。

同设备同年同月抄表唯一。printerCode 不应作为跨系统唯一身份，应使用稳定记录 ID 并结合供应商、订单和生命周期核对。

### 必须保留的业务语义

- 一张订单对应一个客户、一个安装地址、一个供应商及共同租期，可以有多条套餐明细。
- 默认租期三年（加三年减一天），合同特别约定优先。
- 押金默认每台 2,000 元；特殊调整是文档确认规则，Web 尚未完整实现。
- 黑白等价用量 = 黑白用量 + 彩色用量 × 10；比例被确认为长期不变。
- 各台设备、各月份免费额度独立，不跨机共享；当前季度算法是各月结果相加，不是季度额度池。
- 进场当天计费，退场当天不计费；月租和免费量按在场天数折算。
- 客户应收 = 折算月租 + 超额用量 × 单价；金额通过确定性函数计算。
- 运营毛利 = 应收 − 应付，不是净利润；供应商价格缺失则应付/毛利未知。
- 累计表数与月用量不同；跨月缺抄时差额不能直接当成某一自然月的真实用量而不说明。
- 资料不全、同名主体、重复设备码、价格版本不明时，需要核实，不能让 AI 补造。

## 8. AI 讨论范围：先选数据落点，再选交互方式

本节是下一阶段的讨论框架，不是实施方案，也不包含当前供应商产品能力或价格承诺。

需要比较的两条路线：

| 路线 | 可复用内容 | 需要回答的问题 |
|---|---|---|
| 继续 Web + 增加 AI 助手 | 当前数据模型、权限入口、校验和金额函数 | 是否愿意继续维护/部署？如何补服务接口与数据保护？ |
| 企业微信智能表 + WorkBuddy | 现有业务规则、八表结构与操作指令草案 | 是否真的具备附件读取、关联查询、可靠写入、权限、回滚与计算能力？须实测平台能力 |

如果两个系统并存，必须先指定唯一正式数据源、稳定 ID 和同步规则。避免两边都可编辑而没有冲突处理。

适合讨论的候选场景：

1. **只读运营问答**：查订单、设备、待抄表、缺资料；回答带期间、来源记录及缺失信息。
2. **资料转录草稿**：从合同、订单或抄表照片提取候选字段，展示来源片段，人工确认后写入。
3. **异常提示**：发现读数倒退、异常增长、缺月、成本缺失、重复资料。异常不等于自动纠正。
4. **辅助办理**：自然语言生成建单、进场、补录的变更草稿；先复用既有校验，再逐步开放写操作。

推荐原则：让 AI 识别意图、提取和解释，让程序做金额、日期、唯一性和状态约束。不能把数据库直接交给模型任意执行 SQL；附件中的文字也不能成为跳过业务规则的指令。涉及金额或历史的写入需要可审阅的变更、稳定幂等标识、操作日志和明确授权边界。

这些只是架构边界，具体采用什么模型、产品、接口和开发步骤留给下一段 Chat。

## 9. 建议推进顺序与验收标准

1. 决定 Web 还是智能表为正式台账，选定唯一规则文档，并确认存量数据来源。
2. 先明确并修复历史抄表、删除保护、缺抄结算及供应商价格链条。
3. 用真实但脱敏的小样本跑通一次：建单 → 进场 → 首次抄表 → 连续月份 → 补录/更正 → 换机/撤机 → 结算复核。
4. 再试只读问答与录入草稿；评估节省时间、字段正确率、漏项、重复写入和错误金额的情况。
5. 最后讨论扩大自动执行范围。

最低验收样例：补录 7 月后 8 月基数与用量正确；有历史设备不能被普通删除带走记录；当期缺一台抄表时结果明确标为不完整；已确认金额修改有版本与原因；重复提交不重复建单；供应商缺价显示未知；手机能完成所需操作；备份可以恢复。
